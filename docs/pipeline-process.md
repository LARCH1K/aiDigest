# Как работает пайплайн aidigest — по шагам

Документ описывает один запуск сбора: что происходит на каждом шаге, где это в коде, какие проверки защищают от выдуманных цифр и что получается на выходе. Для примера взяты цифры реального запуска от 08.11.2026.

## Коротко

```
 0. Подготовка         проверка лимита Tavily, бюджет запуска, загрузка конфигов и базы
 1. Поиск              14 запросов в Tavily → статьи с полным текстом
 2. Фильтр новизны     уже обработанные URL пропускаются
 3. Извлечение         LLM находит в статье кейсы и показатели
 4. Проверка цифр      каждая цифра сверяется с текстом статьи (без LLM)
 5. Дедупликация       новый кейс сравнивается с базой; дубль сливается
 6. Подтверждение      поиск второго независимого источника для цифр
 7. Сохранение         транзакции PostgreSQL
 8. Выгрузка           Excel с сайта и отчёт запуска
```

| Шаг | Кто работает | Расход |
|---|---|---|
| Поиск | Tavily | 1 кредит за запрос |
| Извлечение | LLM (GigaChat через LiteLLM) | 1 вызов на статью (+1 повтор при битом JSON) |
| Проверка цифр | Python, без внешних сервисов | — |
| Дедупликация | Python + LLM | 1 вызов, если в базе есть кейсы того же региона |
| Подтверждение | Tavily + LLM + Python | 1 кредит + 1 вызов LLM на кейс |

Пример запуска 08.11.2026: 14 поисков → 140 статей → 56 новых → 30 новых кейсов и 16 обновлённых → 16 подтверждений из 27 в очереди. 30 кредитов Tavily, 117 вызовов LLM.

## Шаг 0. Подготовка запуска

Код: `src/aidigest/cli.py` → `cmd_run`.

1. **Настройки** читаются из `config/settings.yaml`. Главные:
   - `run_budget: 30` — кредитов Tavily на обычный запуск (`first_run_budget: 100` — на первый сбор в пустой базе);
   - `confirm_share: 0.4` — доля бюджета, отложенная под подтверждение;
   - `freshness_days: 30` — искать материалы не старше 30 дней (переопределяется полем `days` запроса);
   - `max_results: 10` — статей на поисковый запрос сбора, `confirm_max_results: 5` — на поиск подтверждения;
   - `article_max_chars: 12000` — сколько символов статьи отдаётся LLM.
2. **Проверка лимита Tavily.** Пайплайн делает бесплатный запрос `GET https://api.tavily.com/usage` и узнаёт фактический расход за месяц (например, «240 из 1000»). Если Tavily недоступен, расход неизвестен, а сбор ограничен запрошенным бюджетом.
3. **Бюджет запуска** — минимум из запрошенного бюджета и остатка месячного лимита. Если лимит исчерпан, запуск отменяется (код выхода 2). Если остаток меньше 30, бюджет урезается, и об этом выводится сообщение.
4. **Бюджет делится на два пула** (`budget.py`):
   - сбор — 60% (18 кредитов из 30);
   - подтверждение — 40% (12 кредитов).

   Что не потрачено на сбор, после сбора переходит в подтверждение. Обратно не переходит: подтверждению всегда что-то остаётся.
5. **Загрузка остального:**
   - справочник источников `config/sources.yaml` (32 источника с доменами, достоверностью и типом информации);
   - запросы `config/queries.yaml`;
   - PostgreSQL с кейсами и списком уже обработанных URL;
   - дисковый кеш `data/cache/`.
6. **Ключи** берутся из `secrets.env` в рантайме; в лог не выводятся.

Поля запроса `POST /api/runs` для отладки: `budget`, `levels`, `days` и `offline`. Обычный запуск с сайта использует настройки по умолчанию.

## Шаг 1. Поиск статей

Код: `pipeline.py` → `run_cycle`, `search.py` → `TavilySearch`.

Запросы берутся из `config/queries.yaml` по выбранным уровням. Сейчас их 14:

| Уровень | Запросов | Из них только по доменам справочника |
|---|---|---|
| Свердловская область | 6 | 5 |
| Регионы РФ | 4 | 2 |
| Мир | 4 | 2 |

Для каждого запроса:

1. Если у запроса `use_registry_domains: true`, поиск ограничивается доменами справочника для этого уровня. Это сделано, потому что открытый поиск по Свердловской области давал 0–2 релевантные статьи из 10, а поиск по доменам — 6–10.
2. Параметры запроса в Tavily: `search_depth: basic` (1 кредит), `include_raw_content: text` (полный текст страницы, а не только сниппет), `max_results: 10`, `start_date` = сегодня − 30 дней.
3. **Кеш.** Ключ кеша — все параметры запроса. Если такой же запрос уже делался (тот же текст, те же домены, та же дата начала), ответ берётся с диска бесплатно. Поскольку `start_date` меняется каждый день, повторный запуск в тот же день почти бесплатен, а на следующий день запросы идут заново.
4. Перед реальным запросом списывается 1 кредит из пула сбора. Если пул пуст, сбор останавливается, и пайплайн переходит к обработке уже найденного.
5. Из ответа собираются статьи (`Article`): URL, домен, заголовок, текст, дата публикации. Статьи без текста отбрасываются.

Ошибка сети или API на одном запросе не роняет запуск: запрос пропускается, пайплайн идёт к следующему.

## Шаг 2. Фильтр новизны

URL нормализуется (`urls.py`): убираются метки `utm_*`, `fbclid`, `yclid`, `gclid`, якорь `#...` и завершающий слэш, домен приводится к нижнему регистру, а punycode (`xn--...`) раскодируется в кириллицу. Затем URL сверяется:

- со списком `processed_urls` в базе — статьи, обработанные в прошлых запусках;
- со статьями, уже встреченными в этом запуске (одна статья может прийти на несколько запросов).

Повторы пропускаются. В логе это видно как «статей: 10, новых: 3». В запуске 08.11 из 140 статей новых было 56.

## Шаг 3. Извлечение кейсов (LLM)

Код: `extract.py` → `extract_cases`, `llm.py` → `LiteLLMClient`.

### Что получает LLM

- **Системный промпт** (`SYSTEM_PROMPT`) с определением кейса, списком полей, правилами для показателей и критериями методик.
- **Сообщение пользователя:** заголовок, URL и первые 12 000 символов текста статьи.
- `temperature=0`, модель по умолчанию `GigaChat-3-Pro`.

### Что такое кейс (по промпту)

Кейс — конкретное внедрение: известно, **кто** внедрил, **где** и **что** сделано.

Не кейс:
- новости рынка, мнения, интервью без проекта;
- анонсы, обзоры технологий;
- планы «внедрить ИИ» без конкретного проекта;
- отраслевая статистика и рейтинги;
- продажа продукта без названного заказчика.

Отсутствие цифр — **не** причина отказа: пилот без результатов тоже кейс, просто без показателей.

### Что LLM возвращает по каждому кейсу

| Поле | Смысл |
|---|---|
| `country`, `region`, `municipality`, `organization` | кто и где |
| `sector` | госсектор / бизнес |
| `industry`, `ai_technology` | отрасль и технология ИИ |
| `title`, `summary` | название и суть в 2–3 предложениях |
| `stage` | в разработке / пилот / внедрён / масштабирование / неизвестно |
| `is_concrete` + `not_concrete_reason` | LLM сама помечает сомнительных кандидатов |
| `metrics[]` | показатели (ниже) |

Каждый показатель содержит:
- `name` — что измеряли;
- `before` / `after` / `change` — было, стало, изменение;
- `unit` — единица;
- `kind` — факт или план;
- `criterion` — критерий методики;
- `quote` — **дословная цитата** из статьи, в которой стоят эти числа.

Промпт прямо запрещает придумывать, округлять и пересчитывать числа. Нельзя вычислять «было/стало» из процента.

### Обработка ответа LLM

1. **Разбор JSON** (`parse_json_reply`). Принимается чистый JSON, JSON в блоке ```` ``` ````, или первый корректный JSON-объект в тексте. GigaChat иногда возвращает один кейс без обёртки или голый список — это тоже принимается.
2. **Битый ответ** — один повтор с просьбой «только корректный JSON». Если и второй ответ битый, статья считается ошибочной: не попадает в обработанные и повторится в следующий запуск.
3. **Кеш LLM.** Ключ — модель + системный промпт + текст пользователя. Поэтому любая правка промпта в `extract.py` сбрасывает кеш для этих вызовов. Невалидные ответы в кеш не пишутся.
4. **Отсев кандидатов:**
   - `is_concrete: false` → кандидат отсеян с причиной (в логе «Отсеян кандидат»);
   - не указано ни организации, ни региона, ни города, ни страны → отсеян («не указано, кто и где внедрил»).
5. **Уровень кейса** (`methodology.infer_level`) определяется кодом, а не LLM:
   - в регионе, городе или организации есть «свердлов» или «екатеринбург» → Свердловская область;
   - страна Россия → регионы РФ (если регион не указан — подставляется «федеральный уровень»);
   - иначе → мир.
6. **Методика** (`select_methodology`):

   | Сектор | Уровень | Методика | Критерии |
   |---|---|---|---|
   | бизнес | любой | бизнес-метрики | ROI, операционные затраты, время процесса, уровень ошибок |
   | госсектор | РФ и Свердловская обл. | Р-1 (модель Сбера) | скорость, качество, объективность, экономическая эффективность, персонализация |
   | госсектор | мир | М-1 (OECD + UK) | результат услуги, качество и надёжность, производительность и труд, реализуемость и масштаб, сопутствующие риски |

   Карта М-1 включает качественные наблюдения с цитатами и отмечает критерии без данных. Отношение Р-1 равно `Base / Project` для подтверждённых цитатой сопоставимых фактических значений.

7. **Критерий показателя.** Если LLM назвала критерий не из списка своей методики, код подбирает его по ключевым словам в названии показателя (`guess_criterion`). Например, «время», «срок» → скорость; «эконом», «бюджет» → экономическая эффективность. Не подошло ничего → «прочее».
8. Показатель без цитаты выбрасывается сразу.

Пайплайн сопоставляет региональные кейсы с шестью показателями нацплана по подтверждающим цитатам. Цель на 2030 год хранится в справочнике `national_plan.py`. Архивные связи можно заполнить командой `python -m aidigest enrich --limit 10`, используя сохранённые тексты и цитаты. В режиме `--offline` команда использует сохранённые ответы модели.

## Шаг 4. Проверка цифр по тексту статьи (без LLM)

Код: `quotes.py` → `verify_metric`, `extract.py` → `_verified_variant`.

Это главная защита от выдуманных показателей. Каждый показатель получает отметку `quote_verified` (да/нет). Для «да» должны выполниться три условия:

1. **Цитата есть в тексте статьи** (`quote_in_text`).
   - Сравнение после нормализации: регистр, «ё» → «е», разные кавычки, тире и пробелы приводятся к одному виду.
   - Поиск целыми словами: «на 4» не найдётся внутри «на 45%».
   - Цитата должна быть не короче 3 слов, из них хотя бы 2 настоящих слова (не числа и не «млн», «руб»). Обрывок вроде «95%» подтвердил бы что угодно.
   - Цитата с многоточием проверяется по частям: части идут по порядку, между ними не больше 150 символов и нет отрицания («не», «нет», «без», «ни»).
2. **Числа показателя есть в цитате** (`numbers_in_quote`). Все числа из «было», «стало», «изменение» должны найтись в цитате. Понимаются русские записи: «1 500», «12,5», «3,2 млн», «тыс.».
3. **Знак изменения не противоречит словам** (`direction_consistent`). «+23%» при слове «снизилось» — ошибка.

**Подрезка досчитанного.** LLM часто досчитывает недостающее: из «снизилось на 23%» пишет «стало 77%». Если показатель не прошёл проверку, код пробует убрать досчитанную часть (только `change` или только `before`/`after`). Если без неё цитата подтверждается, показатель сохраняется в урезанном виде и с отметкой «проверена».

Непрошедший показатель **не удаляется**, а остаётся с `quote_verified: false`. Кейс получает флаг `цифра_не_найдена_в_тексте`, и человек может посмотреть на него сам.

## Шаг 5. Дедупликация и слияние

Код: `dedup.py` → `find_duplicate`, `merge_into`.

Один и тот же проект часто описывают несколько изданий. Чтобы не плодить копии:

1. **Отбор кандидатов без LLM:**
   - берутся кейсы того же уровня и того же региона. Регион сравнивается по ключу: первое значимое слово, без «область», «край», «республика», 6 букв. Вся Свердловская область — один ключ;
   - кандидаты сортируются по числу общих слов в организации, технологии и названии;
   - берутся 5 лучших.
2. **Если кандидатов нет** — кейс новый, LLM не вызывается.
3. **Если есть**, LLM получает новый кейс и кандидатов и отвечает, описывает ли какой-то кандидат **тот же проект** (та же организация или регион и та же система), а не просто похожий.
4. **Слияние** (`merge_into`), если дубль найден:
   - источники нового кейса добавляются к старому, без повторов URL;
   - показатель с тем же критерием и теми же числами — не дублируется. Если он пришёл с **другого домена** и его цитата проверена, этот URL засчитывается как подтверждение;
   - новые показатели добавляются;
   - стадия берётся более зрелая (пилот → внедрён → масштабирование);
   - пересчитывается статус подтверждения.

Ошибка LLM при дедупликации не роняет запуск: кейс просто добавляется как новый.

После каждой статьи база сохраняется на диск, а URL статьи добавляется в `processed_urls`. Если запуск прервётся, уже обработанное не потеряется.

## Шаг 6. Подтверждение вторым источником

Код: `confirm.py` → `plan_confirmation_queue`, `confirm_case`.

Это реализация «глубинной аналитики» из процесса «Аналитики»: найти тот же кейс в другом издании и сверить цифры.

### Очередь

Сначала остаток пула сбора переходит в пул подтверждения. Затем строится очередь из кейсов с показателями и статусом «один источник», в таком порядке:

1. новые кейсы этого запуска, ещё не проверявшиеся;
2. старые кейсы, которые раньше не успели проверить (не хватило бюджета);
3. повторная проверка: кейс уже проверялся, второй источник не нашёлся, и с прошлой попытки прошло не меньше 28 дней (`recheck_after_days`). Повторов не больше 2 (`max_rechecks`), то есть всего до 3 попыток на кейс.

### Проверка одного кейса

1. **Поиск в Tavily** (1 кредит из пула подтверждения).
   - Запрос: регион + организация + технология + название кейса.
   - Домены, где кейс уже найден, исключаются: нужен *независимый* источник.
   - При повторной проверке ищутся только материалы, вышедшие после прошлой попытки.
   - До 5 результатов.
2. Независимость проверяется ещё раз кодом: статьи с «своих» доменов отбрасываются, даже если Tavily их вернул.
3. **LLM-сверка.** LLM получает кейс с пронумерованными показателями и до 4000 символов каждой статьи. Для каждого показателя она отвечает:
   - упоминается ли тот же показатель того же кейса;
   - совпадает ли значение (`agrees: true`) или в статье другое (`agrees: false` + `value`);
   - дословную цитату.
4. **Код проверяет каждый ответ LLM**, прежде чем принять:
   - цитата действительно есть в статье (те же правила, что на шаге 4);
   - исходный показатель сам проверен (`quote_verified`). Непроверенную цифру нельзя «подтвердить»;
   - при согласии — в цитате второго источника стоят **те же числа**;
   - при расхождении — число из `value` есть в цитате, и единицы одного вида (проценты с процентами, абсолютные с абсолютными). Иначе «74 региона» против «70%» сочлись бы противоречием.
5. **Проверка по числам без LLM** (`find_number_confirmations`) — дополнение к осторожной LLM. Показатель засчитывается подтверждённым, если в статье другого издания:
   - упомянуто место кейса (регион, город или собственное имя организации);
   - есть предложение со **всеми** числами показателя, и хотя бы одно из них не мелкое (не 0–10: «5 минут» встречается где угодно);
   - в том же предложении есть слово из названия показателя.
6. Новые подтверждающие статьи добавляются в источники кейса.

### Статус кейса

Пересчитывается после проверки (`recompute_status`):

| Статус | Когда |
|---|---|
| `подтверждено` | хотя бы у одного показателя есть подтверждение из другого источника |
| `противоречие` | хотя бы у одного показателя второй источник называет другое значение (приоритет выше, чем у «подтверждено») |
| `один_источник` | ни того, ни другого |

Если кредиты кончаются посреди очереди, оставшиеся кейсы откладываются до следующего запуска (флаг `подтверждение_не_проводилось`). 08.11 проверено 16 из 27, 11 отложено.

## Шаг 7. Сохранение

Код: `store.py` → `PgCaseStore`.

Кейсы статьи и отметка об обработке URL записываются в одной транзакции PostgreSQL. Затем пайплайн сохраняет итоги подтверждения каждого кейса отдельно. Уже завершённые транзакции сохраняются при прерывании сбора.

## Шаг 8. Выгрузка и отчёт

Код: `export_excel.py`, `services/runs.py`.

Excel скачивается из списка кейсов. Итог запуска сохраняется в истории PostgreSQL, полный лог находится в файле на томе бэкенда.

| Лист | Содержимое |
|---|---|
| Кейсы | по строке на кейс: уровень, страна, регион, организация, сектор, отрасль, технология, название, суть, стадия, методика, показатели одной ячейкой, статус подтверждения, флаги, источники с достоверностью, даты |
| Показатели | по строке на показатель: критерий, было/стало/изменение, единица, факт/план, цитата, источник, «цитата проверена», подтверждающие источники, расхождения |

Сортировка: сначала кейсы с цифрами, внутри — подтверждённые, потом противоречия, потом один источник; затем по уровню.

## Флаги сомнений

Флаги не хранятся, а вычисляются из данных кейса (`models.Case.flags`). Они подсказывают аналитику, на что смотреть внимательнее.

| Флаг | Значит |
|---|---|
| `цифра_не_найдена_в_тексте` | хотя бы одна цитата или число не нашлись в статье (шаг 4) |
| `противоречие_источников` | второй источник называет другое значение |
| `один_источник` | подтверждение искали, но не нашли |
| `подтверждение_не_проводилось` | у кейса есть цифры, но до проверки не дошли (бюджет) |
| `стадия_неясна` | стадия «неизвестно» |
| `нет_измеримых_показателей` | в статье нет цифр эффекта |
| `источник_не_оценён` | домен источника не найден в справочнике `sources.yaml`, достоверность неизвестна |

## Запуск с сайта

Бэкенд принимает запрос на запуск, создаёт запись в PostgreSQL и запускает сбор подпроцессом. PostgreSQL гарантирует один активный запуск. Бэкенд завершает запись по результату процесса. При перезапуске незавершённый сбор получает статус «прервано».
