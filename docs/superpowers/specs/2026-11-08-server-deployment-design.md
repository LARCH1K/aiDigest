# Развёртывание aiDigest на сервере — design

Дата: 2026-11-08. Статус: на утверждение.

## Зачем

Сейчас пайплайн и сайт работают на компьютере разработчика под Windows. Их нужно перенести на сервер, чтобы «Аналитика» открывала сайт из интернета и сама запускала сбор кнопкой. Новые версии будут выкладываться часто, поэтому выкладка должна быть одной командой. После выкладки проект должен месяцами работать без вмешательства команды.

## Что решено с пользователем

- **Сервер:** Linux (Ubuntu/Debian), Docker есть или его можно поставить.
- **Доступ:** «Аналитика» открывает сайт из интернета. Домена пока нет, на первое время это `http://<IP-сервера>` **без HTTPS**. Когда появится домен, добавляется HTTPS. Риск принят: по HTTP пароль и cookie идут открытым текстом.
- **Запуск сбора — только кнопкой** на сайте. Расписания нет.
- **Выкладка — вручную**, одной командой по SSH (`./deploy.sh`). CI/CD не нужен.
- **Уведомлений нет.** О сбое узнаёт тот, кто нажал кнопку: ошибка видна на странице запуска. Поэтому у ошибки должна быть **короткая понятная причина**, а не только трассировка Python.
- На старте всё должно быть **максимально просто**.

## Цели

1. `./deploy.sh` на сервере выкладывает текущую `master` и не ломается из-за данных, которые сервер успел изменить.
2. Перевыкладка и перезапуск сайта **не обрывают идущий сбор**.
3. Два сбора одновременно невозможны, откуда бы их ни запустили.
4. Сервис сам поднимается после перезагрузки сервера и падения процесса.
5. Диск не забивается: кеш, логи и копии базы ограничены по сроку или количеству.
6. Неудачный сбор показывает на сайте причину одной фразой.
7. Локальная разработка под Windows (`python -m aidigest_web`, `python -m aidigest run`, `pytest`) работает как сейчас.

## Не цели

- HTTPS, домен, Caddy/nginx: добавляются позже, когда появится домен. Сейчас достаточно, чтобы это можно было сделать без изменения кода.
- Расписание сборов, уведомления (Telegram, почта), мониторинг.
- CI/CD, автоматическая выкладка по push.
- Несколько серверов, масштабирование, база данных вместо JSON-файла.
- Учётные записи пользователей: остаётся один общий пароль.

## Анти-цели (провал, даже если «работает»)

- `git pull` на сервере падает или затирает базу кейсов.
- Выкладка молча убивает идущий сбор: кредиты потрачены, результат потерян.
- Два сбора одновременно: двойной расход кредитов и перезапись `cases.json`.
- Ключи попадают в образ Docker, git или логи.
- Сайт открыт в интернет без пароля.
- Ошибка сбора показана на сайте как «успешно», например когда все поисковые запросы упали.

## Ограничения

- Стек прежний: Python 3.12+, Flask, waitress. Тяжёлые зависимости не добавлять, Docker и Docker Compose — на сервере.
- Правило из CLAUDE.md «не менять `src/aidigest/` ради фронта» остаётся в силе. Изменения в `src/aidigest/` из этого документа (блокировка сбора, ключи из переменных окружения, таймаут LLM, причина ошибки, очистка кеша) нужны самому пайплайну на сервере, а не фронту. Поэтому они допустимы.
- `litellm.env`, `tavily.env`, `web.env` по-прежнему никто не читает и не печатает. Код загружает их только в рантайме.
- Тесты в сеть не ходят.
- Кредиты Tavily (1000 в месяц) при проверке не тратятся: кнопку «Запустить сбор» на сервере при проверке не нажимать, worker проверять офлайн-режимом или подменой.

## Как устроено

### Контейнеры

`docker-compose.yml` в корне репозитория, один образ (`Dockerfile`), два сервиса:

- **web** — `python -m aidigest_web --host 0.0.0.0 --port 8000`. Порт хоста 80 → 8000 контейнера. Адрес хоста задаётся в настройках compose.
- **worker** — новый процесс `python -m aidigest_web.worker`. Ждёт заявку на сбор, выполняет её, снова ждёт.

У обоих `restart: unless-stopped`, ротация логов Docker (`json-file` с ограничением размера) и часовой пояс `Asia/Yekaterinburg` (моё решение: пользователи из Свердловской области).

### Как кнопка запускает сбор

Сейчас `RunManager.start()` запускает `aidigest_web.runner` дочерним процессом веба. На сервере так нельзя: при перезапуске контейнера web погибнут все его процессы, включая сбор.

Новая схема (на сервере):

1. Кнопка → `RunManager` создаёт в `<data>/web/` заявку (файл) с `run_id`. Проверки остаются прежними: месячный лимит, «уже идёт».
2. worker замечает заявку (опрос раз в несколько секунд), берёт её и запускает сбор так же, как сейчас `runner` (`python -m aidigest run`, лог в `<data>/web/runs/<id>.log`, итог в `<id>.json`).
3. Пока идёт сбор, worker регулярно обновляет **heartbeat** — отметку времени в файле блокировки.

**Как узнать, жив ли сбор.** Сейчас веб проверяет номер процесса. Между контейнерами номера процессов не имеют смысла, поэтому признак жизни — свежий heartbeat (не старше примерно минуты). Устаревший heartbeat означает, что запуск прерван, как сейчас при мёртвом процессе.

**Два режима запуска**, выбираются переменной окружения:
- по умолчанию (локально, Windows) — как сейчас: веб сам запускает `runner` дочерним процессом, worker не нужен;
- на сервере (`docker-compose.yml` задаёт режим) — через заявку и worker.

Признак жизни (heartbeat) один для обоих режимов. В локальном режиме его обновляет `runner`.

### Защита от двух сборов

Блокировка переезжает в сам `aidigest run`: перед началом он берёт эксклюзивную блокировку на файл в каталоге данных (`fcntl`/`msvcrt` или эквивалент из стандартной библиотеки). Если блокировка занята, он завершается с отдельным кодом и понятным сообщением. Это защищает и от ручного запуска из консоли на сервере. Блокировка веба (`run.lock`) остаётся для интерфейса.

### Данные

- На сервере каталог данных — папка хоста (по умолчанию `/srv/aidigest/data`). Она монтируется в оба контейнера как `AIDIGEST_DATA_DIR`. В образе данных нет.
- `data/cases.json` и `data/credits.json` **убираются из git** (`git rm --cached` + `.gitignore`). Локальные копии у разработчиков остаются, но в инструкции нужно предупредить: перед `git pull` этого коммита сделать копию `data/`. Git удалит файлы из рабочей папки у тех, у кого они не изменены.
- **Сервер — главный источник базы** (решение пользователя). После переноса база меняется только на сервере. Обратно на сервер её не заливают, синхронизация в две стороны не нужна. В `docs/deploy.md` есть раздел «как скачать копию базы себе» (`scp` из каталога данных или из `backups/`), а в CLAUDE.md строку «`data/cases.json` (в git)» нужно заменить описанием новой схемы.
- **Первый перенос** — вручную: скопировать текущие `cases.json` и `credits.json` на сервер (`scp`) в каталог данных. Шаги описать в инструкции по выкладке.
- **Копия базы:** после каждого успешного сбора worker кладёт копию `cases.json` в `<data>/backups/` с датой в имени и хранит последние 30. Это моё решение: сбор идёт только по кнопке, поэтому копия при каждом сборе полезнее ежедневной.

### Ключи

- На сервере ключи лежат в env-файлах вне репозитория (по умолчанию `/srv/aidigest/secrets/`) и передаются в контейнеры через `env_file` в compose как переменные окружения.
- Код читает ключи **сначала из переменных окружения**, а если их нет — из файлов в корне проекта, как сейчас. Это касается `LITELLM_*`, `TAVILY_TOKEN`, `WEB_PASSWORD`, `WEB_SECRET_KEY`.
- На сервере `WEB_PASSWORD` и `WEB_SECRET_KEY` обязательны. Без пароля сайт уже сейчас отказывается слушать `0.0.0.0`. Без постоянного `WEB_SECRET_KEY` каждая выкладка разлогинивает пользователей, поэтому при открытии в сеть веб без него тоже не стартует.

### Выкладка: `deploy.sh`

Один скрипт в корне репозитория, запускается на сервере из папки клона:

1. `git pull --ff-only`. Если не проходит, остановиться с понятным сообщением.
2. Собрать образ (`docker compose build`).
3. Прогнать тесты в собранном образе (`pytest -q`). Если упали, остановиться: работающие контейнеры не трогать.
4. Перезапустить web (`docker compose up -d web`).
5. worker перезапустить, **только если сбор не идёт**. Если идёт, скрипт ждёт его окончания (до ~30 минут, печатая, что ждёт), потом перезапускает. Если за это время сбор не закончился, worker **не трогается**. Скрипт печатает «сайт обновлён, сборщик — нет: повторите `./deploy.sh` позже или с `--force`» и завершается с ненулевым кодом. Флаг `--force` перезапускает worker сразу, тогда сбор будет помечен как прерванный. Моё решение: так выкладка никогда молча не убивает сбор. Отсюда требование: формат заявки и heartbeat совместим между соседними версиями, то есть новый web понимает старый worker и наоборот. Если формат меняется, менять его надо с обратной совместимостью.
6. Проверить, что web отвечает (`/healthz`), и напечатать итог.

Первая установка (Docker, папки, ключи, перенос базы) описывается в отдельной инструкции `docs/deploy.md`. Это ручные шаги, автоматизировать их не нужно.

**Доступ к репозиторию и права (мои решения):**
- Публичный ли репозиторий `github.com/LARCH1K/aiDigest`, неизвестно. Инструкция покрывает оба случая: публичный клонируется по HTTPS, для приватного на сервере создаётся отдельный read-only deploy key (SSH-ключ в `~/.ssh` пользователя, который выкладывает; в репозиторий и образ он не попадает).
- `deploy.sh` запускает обычный пользователь сервера из группы `docker`, не root.
- Контейнеры работают не от root, а от UID/GID, заданных в настройках compose (по умолчанию 1000:1000). При установке каталог данных отдаётся этому UID через `chown`. Скрипт на хосте только читает файлы в каталоге данных, писать ему туда не нужно.

### Зависимости

Версии закрепляются lock-файлом (например, `requirements.lock`, полученный `pip freeze` из чистого окружения или `pip-compile`). Образ ставит зависимости только из него. `pyproject.toml` остаётся источником списка зависимостей, а как обновлять lock-файл, описывается в инструкции.

Пути к `config/` и `eval/` вычисляются от расположения кода (`ROOT = parents[2]`). Значит, в образе код должен лежать как в репозитории (`/app/src`, `/app/config`), а не устанавливаться в `site-packages`.

### Надёжность долгой работы

- **Таймаут LLM:** у клиента `openai` явный таймаут (порядка 2 минут) и не больше одного повтора. Сейчас по умолчанию до 10 минут на запрос.
- **Очистка кеша:** ответы Tavily в кеше привязаны к дате (`start_date`), поэтому старше пары недель они не переиспользуются. Их удаляют по сроку (14 дней). Кеш LLM и HTTP маленький и полезный, его держат дольше (например, 180 дней). Очистка выполняется worker'ом перед каждым сбором. На локальную разработку она не влияет, если её не включить.
- **Логи запусков** (`<data>/web/runs/`): хранить последние 100 запусков. Выгрузки `data/out/*.xlsx`: последние 30.
- **`/healthz`** — открытый без пароля адрес, отвечает `ok`. Нужен для проверки в `deploy.sh` и healthcheck Docker.
- **Ограничение попыток входа:** сайт открыт в интернет по HTTP с одним общим паролем, поэтому вход ограничивается по IP (примерно 10 неудачных попыток за 10 минут, хранение в памяти процесса).
- **Готовность к прокси:** когда появится Caddy/nginx с HTTPS, понадобятся `ProxyFix` и флаг `Secure` у cookie, иначе проверка `Origin` в `auth.py` начнёт отвечать 403 (`https` против `http`). Включается переменной окружения, по умолчанию выключено.

### Понятная причина ошибки

- `aidigest run` при неудаче печатает отдельной строкой `Причина: <одна фраза>`. Распознаются как минимум:
  - ключ LiteLLM или Tavily не принят (401/403);
  - LiteLLM или Tavily недоступен (сеть, таймаут, 5xx);
  - нет места на диске;
  - уже идёт другой сбор (блокировка занята);
  - месячный лимит Tavily исчерпан (уже есть, код 2).
- **Все поисковые запросы упали — это ошибка, а не успех.** Сейчас пайплайн пишет каждую ошибку в лог и продолжает, и такой запуск получается «успешным» с нулём статей. Новое правило: если ни один поисковый запрос сбора не выполнился, запуск завершается с ошибкой и причиной. То же, если ни одна статья не обработана из-за ошибок LLM (при наличии статей).
- Страница запуска показывает строку причины над ссылкой на лог: в карточке «Последний запуск» и в истории. Без причины показывается общая фраза «Сбор завершился с ошибкой — подробности в логе».

## Что остаётся строителю

- Формат файла заявки и heartbeat, частота опроса, точный порог «устаревания».
- Как именно `deploy.sh` узнаёт, что сбор идёт (файл блокировки в каталоге данных на хосте или команда в контейнере).
- Базовый образ (`python:3.13-slim` или похожий), многоступенчатая сборка, ставить ли `pytest` в итоговый образ или гонять тесты в отдельной стадии.
- Инструмент для lock-файла.
- Точные сроки хранения, если предложенные окажутся неудобными.
- Текст фраз-причин.
- Тесты: новая логика (заявка → worker, heartbeat, блокировка CLI, ключи из окружения, причина ошибки, очистка, ограничение входа) покрывается тестами без сети, как сейчас. Docker и `deploy.sh` проверяются вручную, без запуска сбора.
