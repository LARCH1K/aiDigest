# Трёхзвенная архитектура aiDigest — design

Дата: 2026-11-15. Статус: утверждено.

## Зачем

Сейчас aiDigest — один образ, из которого запускаются два контейнера (`web` на Flask + Jinja и `worker`). Они договариваются через файлы в `data/web/` (`run.lock`, heartbeat, заявки), база — JSON-файл `cases.json`, образ собирается прямо на сервере (`deploy.sh`: `git pull` → `build` → тесты).

Пользователь хочет **более понятную и надёжную архитектурную модель**: у каждой части одна ответственность и чёткая граница, никаких общих файлов между процессами, выкладка из готовых образов.

## Что решено с пользователем

- Сервис — **три приложения**: фронтенд, бэкенд, база данных. Каждое — Docker-образ; на сервере всё поднимается `docker compose`.
- **Фронтенд — SPA на React + TypeScript.**
- **Бэкенд — один контейнер**: API и сборщик в одном процессе. Сбор — фоновая задача бэкенда.
- **При выкладке никаких проверок «идёт ли сбор» нет.** Перезапуск во время сбора допустим: запуск помечается прерванным (см. «Обрыв сбора»).
- **Образы фронтенда и бэкенда публикуются в GitHub Packages** (GHCR) репозитория `LARCH1K/aiDigest`. **Образ БД туда не кладём** — используется официальный образ.
- **Вход — одна заранее заданная пара логин + пароль** (из `web.env`). Учётных записей, регистрации, ролей нет.
- **MCP пока не проектируем.** Архитектура не должна мешать добавить его позже; если для MCP понадобятся изменения, они внесутся потом.
- **Старые данные не переносим.** После переезда база собирается заново; затем проверяется, что качество сбора не упало, и старые файлы (`cases.json`, `credits.json`, `data/web/`) удаляются.
- Доступные модели через LiteLLM: GigaChat-3-Pro, GigaChat-3-Lightning, GigaChat-2, GigaChat-2-Pro, GigaChat-2-Max, EmbeddingsGigaR, frida-decisions. Можно использовать для развития продукта; механизм выбора модели и ключей можно менять и разносить по файлам. **В этот переезд новые модели не входят** — фиксируем только, что архитектура их не блокирует (см. pgvector).

## Цели

1. Три приложения с чёткими границами: фронтенд только показывает и ходит в API; бэкенд владеет логикой, пайплайном и данными; БД только хранит.
2. Между контейнерами нет общих файлов: фронтенд ↔ бэкенд — HTTP API, бэкенд ↔ БД — SQL.
3. Выкладка на сервере — `docker compose pull && docker compose up -d`, без `git clone`/`git pull`, без сборки на сервере.
4. Образы собирает и публикует GitHub Actions только при зелёных тестах.
5. Функциональность сайта не меньше текущей (см. «Функции фронтенда»).
6. Два сбора одновременно невозможны.
7. Обрыв сбора (перезапуск, падение) не оставляет полузаписанных данных и не блокирует кнопку запуска навсегда.
8. Качество сбора после переезда не хуже текущего.
9. Логика бэкенда вынесена в сервисный слой, а HTTP-обработчики тонкие — чтобы позже MCP стал ещё одним тонким входом над тем же слоем.

## Не цели

- MCP-сервер, токены для агентов.
- Перенос текущих данных из `cases.json` в БД.
- Переписывание логики пайплайна (поиск, извлечение, проверка цифр, дедупликация, подтверждение) — меняется только хранение и точка запуска. Исключение — сохранение подтверждений по одному (см. «Обрыв сбора»).
- Эмбеддинги, FRIDA, смена модели LLM.
- Несколько пользователей, роли, регистрация.
- Расписание сборов, уведомления, мониторинг.
- Защита идущего сбора от выкладки (ожидание, второй контейнер).
- HTTPS/домен — как и раньше, добавляется позже (Caddy перед фронтендом), архитектура это допускает.

## Анти-цели (провал, даже если «работает»)

- Фронтенд или будущий MCP читают БД напрямую в обход бэкенда.
- Секреты (`*.env`) попадают в образ, в GHCR или в логи CI.
- После перезапуска сервера кнопка «Запустить сбор» навсегда заблокирована «идущим» сбором.
- Два сбора одновременно: двойной расход кредитов.
- Цифра в кейсе без ссылки на источник или «додуманная» LLM (правило проекта сохраняется).
- Для разработки на Windows нужен сервер или ручная настройка Postgres сложнее одной команды.

## Подходы

Рассмотренные варианты и почему выбран текущий:

| Решение | Варианты | Выбрано | Почему |
|---|---|---|---|
| Фронтенд | A. SPA React+TS в nginx; B. Flask+Jinja, но данные только через API | **A** (решение пользователя) | Самая чистая граница; фронтенд — статика; тот же API потом используют MCP и другие клиенты. Цена — второй язык и npm в проекте. |
| БД | PostgreSQL; SQLite; MongoDB | **PostgreSQL** (наш выбор, пользователь не возражал) | Кейсы с вложенными показателями/источниками — таблицы + JSONB; русский полнотекстовый поиск; блокировка «один сбор» средствами БД; расширение `pgvector` позже даст поиск похожих кейсов на эмбеддингах без новой СУБД. SQLite слабее как сервер в отдельном контейнере; MongoDB ничего не добавляет. |
| Сборщик | отдельный контейнер `worker` + очередь заявок в БД; фоновая задача в контейнере бэкенда; Redis + Celery | **фоновая задача в бэкенде** (решение пользователя) | Сборы редкие, по кнопке; выкладка ручная. Один контейнер проще; потеря при обрыве ограничена (см. ниже). Redis/Celery — лишнее приложение. Если сборы станут частыми или по расписанию, сбор выносится в отдельный контейнер из того же образа без переделки — он уже отдельный модуль. |
| Выкладка | сборка на сервере (как сейчас); готовые образы из GHCR | **GHCR** (решение пользователя) | Сервер не нуждается в исходниках и сборке; откат — сменить тег. |

## Архитектура

```
 браузер ──HTTP──▶ frontend (nginx: статика SPA, /api/* → backend)
                                   │
                                   ▼
                    backend (FastAPI: API + фоновой сбор)
                       │                     │
                       ▼                     ▼
                  db (postgres:17)     том: кеш Tavily/LLM/HTTP
```

### frontend

- React + TypeScript + Vite; сборка — статические файлы, раздаёт `nginx` (образ `nginx:alpine` с конфигом проекта).
- nginx проксирует `/api/*` на `backend:8000` — наружу публикуется один порт, браузер работает с одним origin (cookie и CORS не нужны).
- Маршрутизация в SPA на клиенте; nginx отдаёт `index.html` для неизвестных путей.
- Тексты, пояснения и подсказки, которые сейчас в шаблонах (`help.html`, пояснения флагов `FLAG_HELP`, пояснения полей на страницах «Запросы» и «Источники»), переносятся во фронтенд или отдаются API — на усмотрение строителя, но смысл и формулировки сохраняются.

#### Функции фронтенда (паритет с текущим сайтом)

| Страница | Что умеет сейчас |
|---|---|
| Вход | логин + пароль; блокировка после 10 неудачных попыток с IP на 10 минут |
| Кейсы (`/`) | список; фильтры: текст, уровень, статус подтверждения, «только с показателями» (по умолчанию вкл.), «скрыть сомнительные», достоверность; колонки «Достоверность», «В базе с»; дата обновления базы |
| Кейс | все поля, показатели с цитатами и ссылками, источники, флаги с пояснениями |
| Выгрузка | скачать Excel (текущий `export_xlsx`) |
| Запуск | кнопка «Запустить сбор»; идущий сбор — минуты и хвост лога с автообновлением; история последних 10 запусков с итогом и причиной; полный лог запуска; кредиты Tavily за месяц, остаток, бюджет запуска |
| Запросы / Источники | содержимое `config/queries.yaml` и `config/sources.yaml` с пояснениями полей (только чтение) |
| Справка | справка о достоверности, флагах, дате «В базе с» |

Ссылки из данных — только `http(s)` (сейчас фильтр `safe_url`); это правило сохраняется во фронтенде.

### backend

- Python, FastAPI, сервер uvicorn. SQLAlchemy 2 + psycopg 3, миграции схемы — Alembic. Миграции применяются при старте контейнера (до приёма запросов).
- Слои:
  - `aidigest` — существующий пайплайн (как сейчас, `src/aidigest/`). `CaseStore` (JSON) заменяется репозиторием поверх БД с тем же смыслом операций; учёт кредитов (`MonthlyUsage`, сейчас `credits.json`) — тоже в БД.
  - сервисный слой — операции продукта: список/поиск кейсов с фильтрами, кейс по id, выгрузка Excel, старт сбора, текущий запуск, история, лог, кредиты, справочники запросов/источников. Вся логика здесь, без HTTP.
  - HTTP API — тонкие обработчики над сервисным слоем, JSON, под префиксом `/api`. Будущий MCP — ещё один тонкий вход над тем же сервисным слоем.
- Конфиги `config/*.yaml` и эталон `eval/` остаются в репозитории и попадают в образ бэкенда (как сейчас).
- CLI сохраняется для разработки и отладки: `python -m aidigest run|export|eval` работает против БД из `DATABASE_URL`.
- `GET /api/healthz` (или `/healthz`) — без входа и без обращения к БД, для healthcheck.

#### Сбор как фоновая задача

- `POST /api/runs` создаёт запись запуска и стартует сбор в фоне внутри процесса бэкенда (поток или отдельный подпроцесс — на усмотрение строителя; подпроцесс проще изолирует падение пайплайна и сохраняет текущий механизм лога и кодов выхода).
- **Один сбор одновременно** гарантирует БД: уникальное ограничение «не больше одного запуска в статусе `running`» (частичный уникальный индекс) или advisory lock. Повторное нажатие — ответ «уже идёт».
- **CLI `aidigest run` против той же БД** берёт ту же блокировку и тоже создаёт запись запуска (с признаком источника «консоль»). Поэтому блокировка и запись запуска живут в общем сервисном слое, а не в HTTP-обработчике. *(Наше решение.)* Отметка «прервано при старте бэкенда» не должна трогать идущий консольный запуск — как это различать, решает строитель (например, по признаку источника или по живой сессии БД, держащей advisory lock).
- Проверка месячного лимита Tavily перед стартом — как сейчас (`fetch_tavily_usage` + локальный учёт).
- Лог запуска и итог (`state`, `exit_code`, короткая причина, строки отчёта) хранятся в БД; хвост лога для страницы запуска читается оттуда. Хранить последние N запусков (сейчас 10 показываются; хранится больше — строитель выбирает лимит).
- Короткая понятная причина неудачи (сейчас `aidigest.failure`) сохраняется.

#### Обрыв сбора

Перезапуск контейнера во время сбора убивает сбор. Чтобы это было безопасно:

1. **При старте бэкенда** все запуски в статусе `running` помечаются `interrupted` с причиной «Сбор прерван перезапуском сервера. Кейсы, которые он успел сохранить, уже в базе.» Так как бэкенд один, при его старте старого сбора точно нет — heartbeat и правило «старше 3 часов — завис» больше не нужны.
2. **Транзакция на статью**: кейсы статьи, их слияние с дублями и отметка URL обработанным записываются одной транзакцией.
3. **Подтверждения сохраняются по одному** (сейчас — один раз в конце, `pipeline.py:158`): после каждого кейса из очереди подтверждения его изменения коммитятся.
4. Кеш Tavily/LLM/HTTP остаётся файловым на томе бэкенда — ответы сохраняются сразу после вызова, поэтому повтор сбора в тот же день почти не тратит кредитов.

### db

- Официальный `postgres:17` с Docker Hub; данные на томе хоста.
- Схема — на усмотрение строителя; ориентир: таблица кейсов (скалярные поля — колонки для фильтров, показатели и источники — JSONB или отдельные таблицы), обработанные URL, запуски (статус, лог, итог), учёт кредитов по месяцам.
- `pgvector` сейчас не включаем; при появлении эмбеддингов образ меняется на `pgvector/pgvector` той же мажорной версии, данные совместимы.
- Резервная копия: перед каждым сбором бэкенд делает `pg_dump` в папку на томе, хранятся последние N копий (замена текущему `backup_cases`). *(Наше решение — сохранить нынешнюю гарантию «копия перед каждым сбором».)*

## Вход и безопасность

- `web.env`: `WEB_USERNAME`, `WEB_PASSWORD`, `WEB_SECRET_KEY`. Сравнение в постоянном времени, как сейчас.
- После входа — подписанная cookie-сессия (`HttpOnly`, `SameSite=Strict`, `Secure` при `AIDIGEST_TRUST_PROXY=1` за HTTPS). Все `/api/*`, кроме входа и healthz, требуют сессию.
- Блокировка входа после 10 неудач с IP за 10 минут — как сейчас. За прокси IP берётся из `X-Forwarded-For` только при `AIDIGEST_TRUST_PROXY=1`.
- Бэкенд без пароля не стартует на внешнем интерфейсе (как сейчас). В compose порт бэкенда наружу не публикуется — доступен только фронтенду по внутренней сети; БД тоже не публикуется.
- Секреты — только `env_file` из `/srv/aidigest/secrets/` на сервере; в образ и CI не попадают. Правила CLAUDE.md про `*.env` сохраняются.

## Сборка и публикация образов

- GitHub Actions на push в `master`: тесты бэкенда (с Postgres как service-контейнер), сборка и проверка типов фронтенда, затем сборка и публикация двух образов:
  - `ghcr.io/larch1k/aidigest-backend`
  - `ghcr.io/larch1k/aidigest-frontend`
- Теги: `latest` и короткий SHA коммита. Публикация — встроенным `GITHUB_TOKEN` (`packages: write`), без личных токенов.
- Если пакеты приватные, на сервере один раз выполняется `docker login ghcr.io` с токеном только на чтение пакетов (описать в `docs/deploy.md`).

## Выкладка на сервере

- На сервере в `/srv/aidigest/` лежат только: `docker-compose.yml`, `.env` (порт, тег образов, пути, UID/GID, пароль БД), `secrets/*.env`, `data/` (тома).
- Выкладка: `docker compose pull && docker compose up -d`. Откат: `AIDIGEST_VERSION=<sha>` в `.env` и то же самое.
- `deploy.sh` либо исчезает, либо сводится к этим двум командам и проверке healthz — без `git pull`, сборки и проверок сбора.
- Сервисы: `frontend` (публикует порт), `backend`, `db` — все `restart: unless-stopped`, ограниченные логи, healthcheck у `backend` и `db`; `backend` стартует после готовности `db`.
- Как получить `docker-compose.yml` на сервер (скопировать вручную, скачать из релиза) — на усмотрение строителя; описать в `docs/deploy.md`.

## Локальная разработка (Windows)

- Postgres — одной командой через Docker Desktop (например, `docker compose up -d db` или отдельный compose для разработки).
- Бэкенд и CLI запускаются из `.venv`, как сейчас, с `DATABASE_URL` на локальную БД.
- Фронтенд — `npm run dev` (Vite) с прокси `/api` на локальный бэкенд.
- Тесты:
  - логика пайплайна и сервисного слоя — без сети и без БД, на подменённом репозитории (как сейчас на `tests/fakes.py`);
  - слой хранения и API — против настоящего Postgres (локальный контейнер / service в CI); внешние сервисы (Tavily, LLM) по-прежнему подменены.
- `.claude/launch.json` обновляется под новый способ запуска для проверки в браузере.

## Переезд

Сервера пока нет, приложение нигде не запущено. Цель — **проект полностью готов к запуску на сервере**: образы публикуются, `docs/deploy.md` описывает первую установку с нуля. Данные на сервер не переносятся — там база соберётся с нуля.

1. Вся работа — **в отдельной ветке**; в `master` она попадает целиком после проверки. CI публикует образы только с `master` (на ветке — только тесты и пробная сборка без публикации).
2. Проверка выполняется **локально**, на том же `docker-compose.yml`, что и для сервера (те же образы, локальные пути и секреты). На новой базе выполняется сбор заново (первый запуск — `first_run_budget`).
3. **Проверка качества** перед удалением старого:
   - `aidigest eval` на эталоне `eval/reference_cases.yaml` — результат не хуже, чем на текущей версии;
   - скрипт сравнения в репозитории сравнивает новую базу со старым `cases.json`: доля кейсов с показателями, доля подтверждённых, доля цифр с проверенной цитатой, распределение по уровням (с поправкой на разный бюджет и окно свежести);
   - результат оценивает сам исполнитель (пользователю отчёт не нужен): при существенном падении — разобраться и исправить до удаления; старое удаляется, только когда качество не хуже прежнего.
4. **Кредиты Tavily на всю работу по переезду (отладка, повторные сборы, проверка) — не больше 250.** Тратить в этих пределах можно без отдельного согласования; перед каждым сбором проверяется остаток этого бюджета.
5. После подтверждения удаляются: пакет `aidigest_web` (Flask, шаблоны), файловое хранилище и файлы запусков (`runs.py`, `worker.py`, heartbeat/lock-логика, `runlock.py`), старые `cases.json`, `credits.json`, `data/web/`, Flask/waitress из зависимостей, `test_litellm.py`, старый `Dockerfile`/`deploy.sh` в прежнем виде. Кеш `data/cache/` сохраняется (переносится на том бэкенда).
6. Обновляются `CLAUDE.md`, `README.md`, `docs/deploy.md`, `docs/pipeline-process.md`.

## Оставлено строителю

- Структура репозитория (например, `backend/` и `frontend/` в одном репо).
- Схема БД, имена таблиц, JSONB против нормализации.
- Поток или подпроцесс для фонового сбора.
- Библиотеки фронтенда (роутер, запросы, UI) — без тяжёлых UI-фреймворков, если не обсуждено; стиль близкий к текущему.
- Формат API (эндпоинты, пагинация списка кейсов — сейчас ~200 кейсов, можно без неё).
- Сколько запусков и резервных копий хранить.
